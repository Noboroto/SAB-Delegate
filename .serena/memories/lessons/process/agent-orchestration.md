# Điều phối subagent — prompt, phạm vi, tiến trình, nhịp wave

- Prompt subagent implement PHẢI ghi tường minh: danh sách file được sửa, tiêu chí đạt, "no test runs — lint + typecheck được phép và BẮT BUỘC (`pnpm typecheck` + `eslint <từng file đã chạm> --max-warnings 0`)", "không commit", "không ghi memory". **Why**: bảo "đừng chạy test" làm agent bỏ luôn lint (166 lỗi lint tới cổng commit); vitest/eslint không thấy TS2783, diagnostics của serena chỉ là tsc không có luật typed-lint (full suite ~366 s, typecheck ~7 s). **How**: dán mẫu này vào mọi prompt; lỗi ngoài danh sách file thì báo, không tự sửa. (nguồn: JudgeHub, attendance-hcmus, SAB-Store)
- Cấm subagent `kill`/`pkill`/`docker compose down|restart|up`; nghi hạ tầng hỏng thì BÁO orchestrator; kiểm thiệt hại bằng `docker ps -a` (không chỉ `docker ps`). **Why**: một fix-agent kill PID giữ port, hoá ra là lõi Docker Desktop, sập networking mọi container kể cả repo khác. **How**: orchestrator tự tra PID/port rồi truyền kết quả vào prompt; không bao giờ kill `tsserver.js`. (nguồn: JudgeHub, attendance-hcmus, SAB-Store)
- Chỉ orchestrator ghi git và serena memory; có thể cưỡng chế bằng hook PreToolUse chặn khi payload có `agent_id`. **Why**: hook chỉ chống tai nạn, không phải sandbox (nhận diện người gọi fail-open, phân loại lệnh shell fail-closed, danh sách tên tool ghi luôn thiếu); hai sự cố nặng nhất (script sửa 2853 chỗ, viết lại văn) đều do không đọc diff. **How**: orchestrator đọc lại diff từng hunk (`git diff --numstat`, thêm≈xoá) của file agent đã sửa trước commit. (nguồn: tcps, JudgeHub)
- Nhiều agent edit-only (lint được, không test/typecheck nặng) chạy song song trên tập file rời nhau, sau đó MỘT agent verify duy nhất; không sửa file web/server khi agent verify trình duyệt đang chạy dev stack watch-mode (hot reload phá lượt verify); không `isolation: "worktree"`. **Why**: tuần tự hoá thừa bị user chỉnh lại; hot reload làm hỏng verify. **How**: chia theo thư mục/module, wave sau chỉ spawn khi wave trước đã commit. (nguồn: Leaderboard)
- Nhịp wave: xong MỖI agent thì cập nhật status plan ngay; xong MỖI wave thì commit (≤ trần file của hook) trước khi spawn wave kế; không spawn git-manager khi còn agent ghi cùng working tree. **Why**: cây chưa commit 200+ file làm chuỗi commit giòn, trộn bản đã review với chưa review. **How**: commit nhỏ, thường xuyên, từng phần đã verify. (nguồn: JudgeHub, Leaderboard, attendance-hcmus, SAB-Store)
- Sau 3 vòng sonnet hỏng cùng một task thì KHÔNG chạy vòng 4 bằng sonnet: gọi `kongming` hoặc vòng nâng cấp `opus` (tối đa 1 cùng lúc, không fable). Brief vòng nâng cấp có 4 điểm: vì sao 3 vòng trước hỏng; sửa MỌI chỗ cùng một invariant trong một lượt; tự review đối kháng trước verify nặng; mọi khẳng định kèm output lệnh thật đã chạy. **Why**: mỗi vòng sonnet đóng đúng mục liệt kê nhưng vỡ chỗ cạnh (lỗi mới rò email, guard chỉ quét `.ts`, báo cáo nói spec đã chạy trong khi vitest `include` không khớp). **How**: đếm vòng theo từng task (vòng = fix → verify còn finding). (nguồn: JudgeHub, Leaderboard, QR-Production-Manager)
- Sau mỗi commit/việc nặng: đọc `git log -1` (không tin exit code), liệt kê (dry-run) tiến trình vitest/node mồ côi và scratchpad CỦA PHIÊN rồi mới kill/xoá, chỉ thứ nhận diện là của mình. **Why**: một lượt vitest mồ côi 38 phút tranh CPU với hook commit; Docker engine đói CPU trả HTTP 500. **How**: `ps -eo pid,etime,command | grep vitest`; đưa vào checklist cuối task. (nguồn: JudgeHub, attendance-hcmus)
- Cổng test: tối đa MỘT lượt test mỗi phiên (agent hoặc orchestrator); `git commit/push` đang chạy tức là hook đang chạy suite → không spawn agent chạy test. **Why**: vitest bão hoà CPU/RAM. **How**: nói rõ "no test runs, lint is fine" trong prompt. (nguồn: JudgeHub, QR-Production-Manager, SAB-Store)
- Verify trình duyệt do ORCHESTRATOR làm trong phiên chính (subagent loại `tester` thiếu `mcp__playwright__*` sẽ trả BLOCKED); agent lái trình duyệt là việc nặng → giữ khoá heavy, tự bật dev, gom 3 viewport × sáng/tối vào một lượt, dừng dev và nhả khoá. **Why**: 04/10/2026 dev stack + Playwright ngoài khoá gây watchdog reset. **How**: xác nhận loại agent có MCP browser trước khi giao. (nguồn: Leaderboard, JudgeHub)
- Phát hiện "pre-existing/out-of-scope" từ agent vẫn là việc phải làm: phân biệt DEFECT (hành vi sai, lỗ bảo mật, test giả, comment chết, API deprecated) với scope chưa làm của plan; reviewer báo lỗi thì orchestrator tự kiểm chứng trước (reviewer sai được). Lỗi tìm được bổ sung vào plan đang chạy rồi sửa tiếp, không lập plan mới, không dừng hỏi. (nguồn: attendance-hcmus, Leaderboard)
- Chủ repo đã nói nhiều lần "agent tự quyết, đừng hỏi duyệt": chạy ≥2–3 reviewer đọc-thuần rồi hành động theo phát hiện đã kiểm chứng; chỉ dừng hỏi cho hành động không đảo ngược (push main = deploy, drop dữ liệu, xoá prod, secret) hoặc quyết định sản phẩm. **How**: setup/verify không phá huỷ thì tự chạy. (nguồn: SAB-Store, ComparableTransaction, Leaderboard)
