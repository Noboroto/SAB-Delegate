# Runtime settings live in Postgres (owner 2026-10-21; pattern studied from JudgeHub + Mailmerge)

- Owner rule: SAB-Delegate stores runtime settings (SMTP, LLM endpoint) in Postgres like JudgeHub/Mailmerge, NOT in env. Env keeps only bootstrap: DATABASE_URL/POSTGRES_*, auth secrets, `LLM_KEY_SECRET` (the AES-256-GCM key, scrypt-derived in `apps/server/src/modules/llm/secret-box.ts`; it also encrypts SMTP password and verified email addresses).
- Measured in the reference repos (code read 2026-10-21): both use a generic `SystemSetting {key, value Json}` table + per-key Zod; NO env fallback for SMTP, no LISTEN/NOTIFY, no env→DB import. Mailmerge: `lib/system-setting.ts`, `lib/smtp-settings.ts` (5 s in-process TTL cache, AAD `<tenant>:smtp`), `lib/crypto.ts` (key-version byte). JudgeHub: `api/src/mail/smtp-settings.controller.ts` (test-send uses STORED config only, 5/10 min rate limit, every attempt audited, `filterSmtpTestError` scrubs), Redis 300 s cache. Leaderboard MCP `smtp_get/smtp_set` patches only fromName/fromAddress.
- SAB choice: typed singleton rows (`LlmConfig`, `SmtpConfig`) instead of a generic table — YAGNI at 2 settings (typed columns get DB CHECKs, no JSON parse layer, no "reject secret keys on generic route" guard). Reconsider at ~5+ heterogeneous settings.
- **How to apply**: password never returned (`passwordSet`), required on first save, empty = keep (read DB not cache); upsert + audit in one `$transaction` (params never secret); undecryptable → "not configured", fail closed; transporter cached by hash of connection params; invalidate on save.
- Prod SMTP that already exists (2026-10-21, Leaderboard `smtp_get`): Gmail smtp.gmail.com:465 secure, password masked by the tool. Copying another app's secret between apps was refused by the auto-mode classifier (Credential Exploration) — owner enters it in the web SMTP tab or tells the Coolify session directly.
