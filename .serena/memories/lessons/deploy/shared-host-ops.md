# Vận hành host Coolify dùng chung

- Build từng image một trên host chung (RAM ~8–10 GB, 4 vCPU, ~12+ container): `build api web` cùng lệnh = 2 lượt `tsc` song song → OOM toàn cục, kernel giết `dbus-daemon` rồi `systemd` của user.slice, và OOM-killer từng giết `sshd` (trông như SSH rớt giữa build). **How**: không build 2 image cùng lúc; đặt `deploy.resources.limits.memory` cho service; kiểm RAM host trước khi build Next+Nest. (nguồn: JudgeHub, data-tuyensinh, coolify)
- Đĩa host: `df -h /` trước build (một lần build ăn ~1,5–19 GB; từng 98% → build hỏng khi giải nén layer). Dọn CHỈ `docker image prune -f` + `docker builder prune -f --filter until=24h` (−14 GB); KHÔNG `-a`/`system prune`/`volume prune`; không `docker compose down -v`. Dừng bằng `docker stop <tên đầy đủ>` (filter `name=jc-minio-1` dính cả container dev). (nguồn: JudgeHub, SAB-Store, QR-Production-Manager)
- Thao tác dài qua SSH (restore, migrate lớn, build tay) chạy trong `tmux` với MỘT tên session mỗi project (vd `sab-deploy`), chạy lại thì `tmux kill-session` rồi tạo cùng tên (không `deploy2`/`deploy-retry`), kiểm `tmux ls`; không dùng tên của repo khác. Hook scout-block chặn lệnh Bash có chuỗi `node_modules`/`build` → ghi lệnh ra file scratchpad rồi `ssh ... 'bash -s' < file`. (nguồn: JudgeHub, Leaderboard, SAB-Store, data-tuyensinh)
- Câu hỏi về mạng/subnet/trust-proxy/cổng/DNS/TLS → đo prod live qua SSH chỉ-đọc (`docker ps/inspect`, `docker network inspect`, `ss -ltnp`, `ip -br addr`, `free`, `df`), không suy từ compose; thay đổi cần user đồng ý. "Đã sửa" chỉ khi có request thật từ ngoài vào (`curl -sSI`: status, Set-Cookie, TLS); đừng chẩn đoán prod bằng `curl localhost:<port>` hay log stack local. `docker logs` rỗng ≠ không có request: gửi probe UA độc nhất rồi grep chính nó, và nhớ có thể có hai lớp proxy. (nguồn: Leaderboard, QR-Production-Manager, data-tuyensinh, JudgeHub)
- Coolify 4.3.23 + Traefik v3.6: mỗi resource có network riêng 10.0.X.0/24; ghim subnet của mình NGOÀI dải default-address-pools; tên container `<service>-<uuid>-<timestamp>`; Coolify API từ chính host `http://127.0.0.1:8000/api/v1/*` (deploy `POST /api/v1/deploy {uuid}` rồi poll `GET /deployments/{uuid}`); token mint qua SSH, mỗi repo một deploy key read-only; secret sinh ngay trên host (`openssl rand`), mode 600, không in. Ghi subnet/tên app vào runbook, không ghi uuid/token. (nguồn: QR-Production-Manager, Leaderboard)
- Không hot-patch trên host: dọn cây (`git checkout -- file`) khi cây chưa bản và nóng là xoá bản vá khỏi đĩa mà container giữ inode cũ vẫn chạy đúng một thời gian → khó truy; tạo nhánh + commit bản vá TRƯỚC khi dọn; cấu hình ngoài repo (Traefik dynamic conf, env trong Coolify UI) ghi vào runbook. Luôn đo `git log -1` + `_prisma_migrations` so với thư mục migration trước deploy. (nguồn: JudgeHub)
- Quyết định chủ host (coolify, 11/10/2026): KHÔNG backup định kỳ (không scheduled dump, không S3/R2/rsync off-site); vẫn BẮT BUỘC `pg_dump -Fc` một lần trước thay đổi DB rủi ro, đếm row trước/sau, dump lưu ngoài working tree (`/srv/appdata/_archive/`). Đừng đề xuất backup định kỳ trong plan. Nếu vẫn có script backup thì phải có restore-test thật. (nguồn: coolify, JudgeHub)
- Xoá resource Coolify không cần UI: `docker exec coolify php artisan tinker --execute=...` gọi `App\Jobs\DeleteResourceJob::dispatchSync(...)`; bind mount `/srv/appdata` KHÔNG bị xoá (tự dọn, dump giữ `/srv/appdata/_archive/`). Trước hành động phá huỷ: nhìn target, có backup, hỏi user. RBAC: một team, owner duy nhất, người khác Member chỉ xem. (nguồn: coolify)
- Monitoring dùng chung: app `monitoring` (Prometheus + blackbox-exporter + Grafana + Loki + Alloy) probe `/health` qua repo multi-domain; log opt-in bằng label `logging=...`, `logging.project`, `logging.service`; `/health` KHÔNG phụ thuộc DB (liveness Nest không gọi DB; 200 của SPA/static fallback không chứng minh asset tồn tại). Nhãn Loki `app` luôn là tên project. (nguồn: coolify, student-papers-manager, JudgeHub)
- Pull image lớn qua ISP/router yếu có thể `TLS handshake timeout` (ONT bão hoà): `daemon.json` `max-concurrent-downloads: 1`, `max-download-attempts: 10` — chỉ áp nếu host nằm sau router yếu. Container dev lạc trên host prod: định kỳ kiểm cổng bằng `ss -ltn` + thử từ ngoài, không tin `ufw status`. (nguồn: JudgeHub)
